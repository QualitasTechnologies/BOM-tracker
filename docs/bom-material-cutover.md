# BOM material cutover boundary

Native material mutations, native PO sends that update linked materials, and the MCP material writer require a server-created `pulseMaterialCutovers/{projectId}` document. They never create or remove the marker during ordinary edits. Before an explicit project cutover, Pulse keeps material editing disabled and the legacy BOM client remains writable under its existing access rules.

After the trusted cutover process creates the marker, Firestore continues to allow signed-in project members to read `projects/{projectId}/bom/data`, but blocks client writes to that document. Nested BOM subcollections and the rest of the project access rules remain unchanged. The marker is not client-readable or client-writable. The legacy `triggerSpecSearch` endpoint checks the marker at entry and again transactionally immediately before calling n8n; its response rechecks both the marker and BOM revision before changing only its target item. There is still a small boundary between that pre-dispatch check and the external HTTP request, so cutover operations must stop new spec-search requests and drain any in-flight calls before creating the marker. Confirm that the deployed n8n workflow only returns search results and does not independently write Firestore before activation.

Marker activation is a one-way operational decision. This stage does not provide marker creation, deletion, automatic rollback, or a rollback path. Keep native feature flags off and do not create markers until a separately reviewed cutover procedure has verified every legacy and external writer (including any Firebase or MCP service outside this repository), paused or fenced legacy edits for the project, drained in-flight requests, and established the team's recovery procedure.

For legacy email PO sends, the callable captures provider acceptance time immediately after the provider returns, persists `acceptedAt` (ISO string), `sentAt` (Firestore timestamp), and `actualSentDate` (Asia/Kolkata date), and returns the two date values for Pulse. The legacy callable does not have a durable provider idempotency journal: if the provider accepts an email but the first Firestore metadata write fails, recovery cannot prove or reuse that original accepted time. The native send flow has a durable acceptance journal; keep this legacy failure window as an open limitation until that send path is retired or journaled.
