# BOM material cutover boundary

Native material mutations, native PO sends that update linked materials, and the MCP material writer require a server-created `pulseMaterialCutovers/{projectId}` document. They never create or remove the marker during ordinary edits. Before an explicit project cutover, Pulse keeps material editing disabled and the legacy BOM client remains writable under its existing access rules.

After the trusted cutover process creates the marker, Firestore continues to allow signed-in project members to read `projects/{projectId}/bom/data`, but blocks client writes to that document. Nested BOM subcollections and the rest of the project access rules remain unchanged. The marker is not client-readable or client-writable. The legacy `triggerSpecSearch` endpoint checks the marker at entry and again transactionally immediately before calling n8n; its response rechecks both the marker and BOM revision before changing only its target item. There is still a small boundary between that pre-dispatch check and the external HTTP request, so cutover operations must stop new spec-search requests and drain any in-flight calls before creating the marker. Confirm that the deployed n8n workflow only returns search results and does not independently write Firestore before activation.

Marker activation is a one-way operational decision. This stage does not provide marker creation, deletion, automatic rollback, or a rollback path. Keep native feature flags off and do not create markers until a separately reviewed cutover procedure has verified every legacy and external writer (including any Firebase or MCP service outside this repository), paused or fenced legacy edits for the project, drained in-flight requests, and established the team's recovery procedure.

For legacy email PO sends, the callable reserves the PO before PDF/provider work, blocks another email or manual mark while the reservation is active, rechecks the project marker transactionally before dispatch, and atomically finalizes the PO, linked material dates/status, vendor-PO document, and audit after provider acceptance. The callable captures `acceptedAt` (ISO string), the Resend email ID, stable PDF/document details, `sentAt` (Firestore timestamp), and `actualSentDate` (Asia/Kolkata date). The attempt ID is also sent as Resend's idempotency key; Resend retains keys for 24 hours, so this is a bounded duplicate guard, not a substitute for the cutover drain or an operator procedure for older ambiguous results. An admin can release a reservation stuck in `preparing` only after 15 minutes, through an audited callable that verifies provider dispatch never began; this may clear an orphaned pre-dispatch lock after a project marker exists because it does not write BOM data or contact the provider. An admin can replay atomic finalization from durably recorded provider acceptance through a separate callable; it does not resend the email. Definitive named Resend 4xx rejections release the reservation, while network errors, 409s, 5xx responses, and unknown outcomes remain locked for reconciliation.

The PO inward safety stage adds a pre-cutover `legacyMarkPurchaseOrderSent` callable. It is admin-only, validates the explicit actual sent date, and atomically updates the PO, linked BOM item order/arrival fields, and an audit/operation receipt. Its Pulse client retains the same operation ID across reloads for a confirmed retry. Both legacy callables check the per-project cutover marker; uncut projects continue using the legacy flow during staged rollout even when native procurement is enabled globally.

An accepted email whose provider ID and finalization payload were durably saved can be finalized later by an admin without another send. For the crash window before that write, the attempt stores a server-only frozen email payload and a unique create-only copy of the exact PDF bytes. The copy has a byte count and SHA-256 recorded with the retry payload; retries verify both before attaching it. The immutable copy becomes the vendor PO document URL after finalization and is retained as the canonical record of exactly what was sent. Successful retry and accepted-send recovery remove the private email retry payload but keep that PDF. Definitive named Resend rejections release the reservation with an audit record and remove retry-only objects; stale pre-dispatch release removes both orphaned temporary objects because no provider send began. Acceptance timestamps and provider IDs use transactional compare-and-set checks so concurrent initial sends and retries cannot replace already-recorded evidence. An admin retry waits ten minutes if the original callable is still marked `dispatching`, then uses the same Resend idempotency key for up to 23 hours, reads the provider's creation time, and runs the atomic finalizer. If no provider ID was saved and the idempotency window has expired, the system stays locked for manual provider verification rather than risking a duplicate. The email reservation prevents competing PO actions, but the current cutover process does not yet prevent marker creation while a reserved email is in flight. If that happens, finalization fails closed and leaves an accepted/uncertain lock for reconciliation, with the PO/material transaction uncommitted. There is not yet a cutover drain endpoint or a complete operator procedure for older ambiguous results. Marker creation must remain disabled until a separately reviewed procedure stops new legacy sends, rejects cutover while any legacy send attempt remains active, drains in-flight requests, and establishes recovery for older ambiguous results. Before a marker is created, the cutover preflight must confirm there are no purchase orders with a non-null `legacySendAttemptId` and no unresolved records under `pulseLegacyPOSendAttempts/{projectId}/attempts`; each `preparing`, `dispatching`, `uncertain`, `provider_accepted`, or `needs_reconciliation` phase must be completed or explicitly reconciled. Check and fence external Firebase/MCP writers too. Do not treat these unit tests as evidence that production cutover is safe.
